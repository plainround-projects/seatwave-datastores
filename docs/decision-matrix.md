# SeatWave database decision matrix

Six workloads, each matched to a data model from its access patterns. Rates are Module 1's arena peak on the reference machine (4 vCPU, 16 GB, one SSD at 3,000 IOPS, one region) unless a row says otherwise; every rate and size is an estimate from `SizingCli` (Module 15, Section 7) unless it is marked measured. The measured numbers come from the lab Redis of this project on a laptop, 12 November 2026 (Module 15, Section 8), and from Module 14's study of PostgreSQL; neither is production's. Stores already on call before Module 15: PostgreSQL 18.6 (Module 13) and Redis 8.10.3 (Module 12, rate limiting).

| Workload | Access patterns (peak rate, consistency) | Data model | Store | Why this one | Rejected, and why |
|---|---|---|---|---|---|
| Sessions | S1 read by session id 33,333/s; S3 touch 13,333/s; S2 sign-in 555/s; S4 sign-out 56/s; S5 a fan's devices 1/s. Read your own writes; losing 1 s of sessions in a crash is acceptable (fans sign in again). | Key-value with time-to-live | Redis 8.10.3, its own instance (append-only file every second) | Every pattern is a get or put by key; expiry is built in; 2.19 GiB fits in memory (measured: 480 bytes a session, 0.89 GiB for 2,000,000 of this design's values); about 31% of one command thread at peak (measured: 27 to 34% at the peak rate, about 1 µs to execute a command) | PostgreSQL table: 13,333 updates/s, about 1.98 cores at Module 14's measured CPU per write (1.73 by its estimate), beside 2.21 cores for the hold inserts, over the 4 vCPU; and a sweeper for 555 expiries/s adds dead rows and index writes to the system of record. Document store: no query looks inside a session. |
| Catalog | Event page reads one event whole 20,000/s; event list by venue and date (Module 14's Q4); edits a few per day. Read committed is enough; a stale price for seconds is not (prices are checked again at hold). | Document (event with venue and sections nested) | PostgreSQL 18.6, a `jsonb` column beside `events` | One read returns the page; 3.6 MiB for 5,000 events; no new system; Module 16 caches it | A document database: same model, one more system to run for 3.6 MiB. Key-value: cannot serve the list by venue and date without a hand-made index. |
| Orders | Confirm 200/s (Module 2), in one transaction with the hold; my tickets by customer and date; door list by event. Serializable rules (Module 13). | Relational | PostgreSQL 18.6 (`bookings`, `holds`), the system of record | Transactions across holds, seats and bookings; Module 14's indexes serve every listed query; 5.09 GiB a year | Wide-column (`bookings_by_customer`, `bookings_by_event`, Lab 3): serves both reads at any size, but no transaction with the hold; kept as the design for a history copy if one is ever needed. |
| Seat map | Read one section 20,000/s; hold 13,333/s with "one seat, one owner". Strong: a seat shown free must be claimable or refused, never sold twice. | Relational | PostgreSQL 18.6 with `one_claim_per_seat` and `one_seat_per_number` | The claim rule needs a unique index inside the hold's transaction (Modules 13 and 14) | Key-value claims: the rule would move into application code; a hot event's key would sit on one partition (`HotPartitionCli`: 13,333/s on one partition against a 1,000/s ceiling). |
| Fan graph | "Which of my companions go to this event?" 1 hop, about 500/s (assumption); "companions of companions" 2 hops, rare. Read committed. | Relational edge table (graph-shaped data) | PostgreSQL 18.6, a new table `companions (customer_id, companion_id)` | 1 and 2 hops are 20 and 400 index lookups; 50,000,000 edges fit | Graph database: pays off from 3 hops or path queries (8,000 fans at 3 hops), which no SeatWave screen asks today. |
| Metrics | Write 100,000 points/s; read by series and time range for dashboards and alerts; keep raw 15 days, then roll up. Losing seconds of points is acceptable. | Time series | A time-series store (Prometheus is the example; version 3.16.0 checked 11 November 2026) | Compressed about 11.0 GiB a day against 643.7 GiB as PostgreSQL rows; retention by time is built in | PostgreSQL: 100,000 inserts/s need about 3.6 machines' worth of insert capacity at the 143 µs of CPU per insert Module 14 measured (2.9 by its estimate). Wide-column: can hold it, without the query language and compression. |

**Systems on call after this decision:** PostgreSQL, Redis (now two instances: rate limits, sessions) and one time-series store. One new system family, not five.

**The result in one sentence:** Bookings and seats stay relational because their rules need transactions, sessions move to Redis because every pattern is a key lookup with expiry, metrics go to a time-series store because PostgreSQL cannot absorb 100,000 points a second, and the catalog and fan graph change model, not database, because a new system would cost more than it saves.
